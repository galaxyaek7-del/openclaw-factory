### 💰 الفلسفة الاستراتيجية — شركة استثمار رقمي (توجيه المؤسس، 2026-07-23)

Galaxy Forge ليست شركة برمجيات — هي **شركة استثمار رقمي**. الكتب، القوالب، الأدوات، الكورسات هي أدوات استثمار، لا غاية بحد ذاتها. السؤال الدائم قبل أي بناء: "هل هذا يزيد القيمة طويلة المدى للشركة؟" — وليس "ماذا يمكننا أن نبني؟" (راجع `value_engine.py`، ADR-102 — الأداة الحقيقية التي تُجيب على هذا السؤال فعلياً لكل فرصة مقبولة اليوم).

**مبدأ الحياد التقني:** لا ولاء لأي موديل ذكاء اصطناعي أو شركة أو منصة بعينها (Claude, GPT, Gemini, DeepSeek, Qwen, Kimi, Doubao, نماذج مفتوحة المصدر — جميعها أدوات إنتاج مرشَّحة). معيار الاختيار الوحيد: نتائج أفضل، جودة أفضل، سرعة أفضل، موثوقية أفضل، اقتصاديات أفضل، نتائج أفضل للعميل. الأداة الحقيقية لهذا موجودة بالفعل: `ai_capability/registry.py` (Technology Investment Council) — يُسجِّل بيانات حقيقية لكل مزوّد فعلاً تم استدعاؤه (Groq اليوم)، ويُبقي كل مزوّد آخر (بما فيهم Kimi/Doubao المُضافان 2026-07-23) بحالة DISCOVERY صريحة حتى تتوفر بيانات اعتماد حقيقية واستدعاء حقيقي فعلي — لا مقارنة أداء مُختلَقة أبداً.

**التوسّع العالمي / برنامج الصين الاستراتيجي — مؤجَّل بوعي، ليس متجاهَلاً:** التوجيه نفسه (2026-07-23) طلب معاملة كل دولة كفرصة استثمار مستقلة (أمريكا، الصين، اليابان، كوريا الجنوبية، ألمانيا، بريطانيا، الهند، جنوب شرق آسيا، الشرق الأوسط) و"شعبة استخبارات صين" دائمة. بحث حقيقي (2026-07-23) وجد صفر موصّلات بيانات محلية حقيقية لأي من هذه الأسواق (لا Baidu/WeChat/Xiaohongshu/Douyin، ولا أي مصدر محلي آخر لبقية الدول) — المصدرين الخارجيين الوحيدين الحقيقيين في هذا المصنع (Hacker News + GitHub) عالميان/إنجليزيان، لا يمثّلان استخبارات سوق محلية حقيقية. هذا يتعارض أيضاً مباشرة مع **القاعدة الذهبية أعلاه** ("لا توسع بمنتج جديد قبل أول دولار من المنتج الحالي") — وصفر مبيعات حقيقية مكتملة موجودة على أي قناة حتى الآن. **القرار (تأكيد المؤسس، 2026-07-23):** توثيق الفلسفة الآن (هذا القسم)، لا بناء وحدات استخبارات سوق قُطرية بعد. يُعاد النظر عند: (أ) أول دولار حقيقي فعلي، أو (ب) توفّر موصّل بيانات محلي حقيقي فعلي — أيهما أسبق.

**شعبة استخبارات التجارة العالمية (GCID) — مؤجَّلة بالكامل (ADR-148، 2026-07-30):** طلب المؤسس بناء شعبة أعمال دائمة جديدة (تسويق بالعمولة/شراكات تجارية عالمية) كمحرّك إيراد أساسي. تحقّق مباشر قبل كتابة أي كود: هذا المصنع بلا أي دولار حقيقي حتى اليوم — السجل "الوحيد" في finance_data.json اسم منتجه الحرفي `"contract-test-ladder-DELETE-ME"` (سجل اختبار دخان)، وسجل الحقيقة الأصعب `config/reality.json` (المصمَّم عمداً بحيث "لا يمكن للمصنع تزوير هذه الأرقام") يُظهر `published_books: []` — صفر منتج حقيقي منشور على أي قناة. هذا نفس شرط **القاعدة الذهبية أعلاه** بالضبط الذي أوقف التوسّع العالمي أعلاه. **القرار (تأكيد المؤسس عبر AskUserQuestion، 2026-07-30):** توثيق فقط (ADR-148)، لا بناء أي كود. يُعاد النظر عند: (أ) أول دولار حقيقي فعلي (تحقَّق عبر `config/reality.json` الحقيقي، لا `finance_data.json` الخام)، أو (ب) تجاوز صريح من المؤسس لهذه القاعدة تحديداً لهذه المبادرة.

## Architecture

**Galaxy Forge** is an Arabic-language (RTL) dashboard for a self-publishing business selling digital products on KDP, Etsy, and Gumroad.

### Stack

| Layer | Technology |
|---|---|
| Frontend | Single-file vanilla HTML/CSS/JS (`index.html`), Arabic RTL, no framework |
| Backend | Express 5 (`server.js`), port 3000 |
| AI | Groq SDK — `llama-3.1-8b-instant` via `POST /chat` and `POST /api/agent/:name` |
| PDF generation | Python + reportlab (`book_generator.py`) |
| Data | `finance_data.json` (flat JSON, written directly by server) |

### Key flow: book generation

The browser calls `POST /generate-book` → `server.js` spawns a Python subprocess (`book_generator.py --json`) → passes parameters via `stdin` as JSON → reads JSON result from `stdout`. The PDF is written to the project root directory with a filename derived from the book title.

`book_generator.py` is standalone and can be run directly:
```bash
python book_generator.py          # generates demo_cookbook.pdf
```
When invoked with `--json`, it reads a JSON object from stdin:
```json
{"title":"...", "subtitle":"...", "type":"journal", "theme":"blue", "pages":120, "author":"...", "output":"filename.pdf"}
```
Supported `type` values: `journal`, `planner`, `habit`, `gratitude`, `fitness`, `tracker`, `healthy_eating`, `budget`, `mindfulness`, `cookbook`.

### Agent endpoints

`POST /api/agent/:name` — **live Groq calls**, not stubs. **Gated behind `requireMissionControlAuth` since the Enterprise Security & Cyber Defense Mission's Phase 1 Security Audit (2026-07-23, finding 2.1)** — this route previously had zero authentication, meaning anyone who could reach it could spend the founder's real Groq API budget with an arbitrary `message` and no rate limit; that is now fixed. A logged-in Mission Control session (via `mission_control_login.html`) is required before `index.html`'s own buttons that reach this route will work — the same real prerequisite `/finance/add` already had before this fix, now extended here and to most other previously-open routes (see `ENTERPRISE_UPGRADE_ROADMAP.md`'s finding 2.1 for the full route list and which ones instead accept `INTERNAL_SERVICE_TOKEN` for real internal automation callers that have no browser session). Each of the six agents has a dedicated `system` prompt defined in the `AGENT_PROMPTS` object in `server.js` (lines 127–190):

| Agent | Role |
|---|---|
| `scout` | Market analysis — trending niches, pricing, competition level |
| `builder` | Content generation — book structure, sample pages |
| `design` | Cover & interior design ideas for 6×9 inch books |
| `qa` | Quality checklist, common KDP/Etsy rejection reasons |
| `publisher` | SEO-optimised titles, descriptions, keywords, Amazon categories |
| `finance` | Pricing strategy, profit margins per platform, break-even |

Each agent accepts an optional `message` in the request body; if omitted, a default `trigger` prompt fires automatically. `index.html` only wires UI buttons for `builder`/`design`/`publisher`/`qa` — the bare `scout` and `finance` agents above are live and reachable via `POST /api/agent/scout` / `POST /api/agent/finance`, but have no UI trigger (the fuller `/api/scout/run` pipeline below is what the UI's Scout button actually calls).

There is also a separate, more complete Scout pipeline: `POST /api/scout/run` runs a real end-to-end chain — Groq market brief → pricing (`getButterPrice()` in `factory_loop.js`) → niche safety filter (`safety_filter.py`) → `book_generator.py` → auto-distribution (`autoDistributeScoutBook()` → `distributor.py`). This is distinct from the simple `POST /api/agent/scout` text-analysis call above and is what the dashboard's Scout button triggers.

`POST /chat` (`server.js:1768`) — a raw Groq passthrough (any `message` in the request body goes straight to `llama-3.1-8b-instant`). Confirmed via full-repo audit (STRUCTURAL_DIAGNOSIS.md disease #8) to have **zero callers**: not `index.html`, not `factory_loop.js`, not any test, not any other doc. Predates the six-agent `POST /api/agent/:name` system above and was superseded by it in every practical sense. **Gated behind `requireMissionControlAuth` since the Full Factory Integrity Audit (2026-07-22)** — this line previously described it as unauthenticated; that was fixed in code but never updated here until now. Still zero real callers, so still a candidate for removal rather than a route to build on.

It computes nothing new and fabricates no metric — a section with no data yet reports that honestly (e.g. `tier1_discovery.accepted` is 0 today, matching `ADR-035`/`ADR-036`'s real finding, not an invented KPI). `lib/dashboard_data.js` has no Express/`child_process` dependency, so it's unit-tested in isolation (`tests/test_dashboard_data.js`) without needing a live server.

`GET /health` (`computeHealthStatus()`, `server.js`) gained real infrastructure checks (Enterprise Infrastructure & HA Mission, 2026-07-23, finding 4.7): memory, CPU (honestly reports `os.loadavg()` as unavailable on Windows rather than faking a number), disk space (Windows-only today — no POSIX deployment exists yet to build a cross-platform check against), real network reachability to this factory's actual external dependencies (Groq, Telegram if configured, GitHub), and `storage_integrity` — real per-line JSON/JSONL validation of `data/decisions.jsonl`/`finance_data.json`/`data/factory_state.json`, the honest analog to "database health" for an architecture that has none. `database`/`queue_system`/`worker_pool` are reported as explicit `not_applicable` (never a fabricated green check) — this factory has no database, no message queue, and no worker pool. Logic lives in `lib/health_checks.js`, same no-Express-dependency isolation-testing pattern as `lib/dashboard_data.js` (`tests/test_health_checks.js`).

### Customer Platform

`customer_site/` is Galaxy Forge's real public customer-facing platform, served at `/site/` — a separate, English, dark-themed surface from the founder-facing Arabic Mission Control. Built across Phase 1/2 Round 1 (ADR-129/130, 2026-07-25) and Rounds 1-6 (ADR-131, 2026-07-29). Real end-to-end pipeline: intake → Qualification/Pricing (reuses `decision_engine.evaluate_and_decide`/`profit_oracle.butter_price`, the same real engines every internal opportunity uses) → real contract generation + typed-name e-signature acceptance → real Paddle checkout attempt → real payment-completion check + invoice → honest Production/QA/Delivery routing → real download center → real customer reviews.

- **Accounts**: `lib/customer_auth.js` (scrypt password hashing, its own signed-cookie session — deliberately separate from Mission Control's `mc_session`, zero new npm dependencies). `POST /api/customer/signup|login|logout`, `GET /api/customer/session`, `customer_site/login.html`. Guest (no-login) submission remains fully supported; a logged-in visitor's `account_id` is stamped onto their request for later history matching (by `account_id` OR email, reconciling pre-account guest requests).
- **The pipeline** (`customer_pipeline.py`, all commands spawned directly from `server.js`, not via `mission_control_api.py` — a different, customer-facing trust boundary): `advance_request` → `approve_request` (now requires `accepted_name`, a real contract e-signature via `contract_generator.py`) → `_attempt_payment_verification` → `check_payment_status`/`check_all_awaiting_payments` (real Paddle transaction confirmation + `invoice_generator.py`) → `_fulfill_paid_request` (honest routing: reuses an already-published `books/_generation_log.jsonl` artifact for a matched catalog product, else the side-state `PENDING_FOUNDER_FULFILLMENT` for a genuinely bespoke request, resolved via the founder's own `fulfill_manually()`) → `list_requests_for_account`/`submit_review`/`mark_followed_up`.
- **Real gap disclosed, not built**: customer-facing email/SMS notification is 0% built — the pull-based `customer_site/status.html`/`history.html` pages are the real substitute today. Every stage transition still notifies the founder via the existing Telegram channel.
- **Still genuinely blocked**: Paddle's account-onboarding gate (`transaction_checkout_not_enabled`) — every `PAID`-and-later code path is real but stays functionally unexercised against a live account until the founder clears it in `vendors.paddle.com` (`scripts/check_paddle_checkout_status.py` re-checks this live, never from cache).
- **Mission Control** gained a real executive cockpit for all of the above: `mission_control_executive_v1.html`'s card grid has panels for Customer Accounts, the Customer Pipeline, the Production/Fulfillment Queue, Invoices, and Reviews — all pure passthrough over the real state above, zero new dashboard file, zero fabricated metrics.

### Autonomous Company Evolution Engine

`evolution_queue.py` (new, ADR-133, 2026-07-29) is the real Observe → Think → Simulate → Decide → Execute → Learn → Protect → Dashboard pipeline the founder's "AUTONOMOUS COMPANY EVOLUTION ENGINE" directive asked for. **Execute is, by explicit founder decision, human-gated always — this must not be loosened without asking again.** No proposal, regardless of its computed risk tier, executes automatically: every real proposal from `tool_intelligence/proposals.py::list_proposals()` (6 real signal sources as of Global Trust & Resilience Layer Round 1, 2026-07-29 — bottlenecks, technical debt, capability gaps, a stuck-customer-funnel signal, a marketplace-publish-protection signal, and a health-degradation-trend signal) is intook, mechanically simulated (`affected_modules`/`rollback_complexity`/`sensitive_areas_touched` — a disclosed static evidence-text heuristic, not a real execution sandbox), and decided (real `policy_risk`/`duplicate_architecture_risk` flags, never an auto-approve/auto-reject) into a real state machine in `data/evolution_queue_state.json`: `PROPOSED → SIMULATED → AWAITING_FOUNDER_APPROVAL → APPROVED/REJECTED → IMPLEMENTED`.

`factory_loop.js`'s daily tick (`maybeGenerateDailyEvolutionQueueIntake()`) runs intake/simulate/decide once per calendar day — it stops at `AWAITING_FOUNDER_APPROVAL` and never calls approve/reject/mark-implemented. Those three are exclusively founder-triggered Mission Control actions (`POST /api/v1/actions/approve-evolution-proposal|reject-evolution-proposal|mark-evolution-proposal-implemented`, each requiring `{ proposal_id }`) — the one concrete code enforcement of "human-gated always," not just a policy note. `mark_implemented()` only closes the loop after a real, separately-reviewed Claude Code session has actually shipped an `APPROVED` proposal; there is no code path that writes production code from this system itself. Its `note` field is this factory's real "lessons learned" record (Decision Memory, Round 6, 2026-07-29) — not duplicated with a second field elsewhere.

**Outcome measurement + ranking (ADR-143, 2026-07-30)**: the founder's follow-up "AUTONOMOUS EVOLUTION ENGINE" directive asked this pipeline to "continuously measure whether every implemented evolution actually improved" revenue/reliability/scalability/automation/customer value/execution speed, and to rank proposals by strategic value/revenue impact/execution cost/long-term sustainability/risk/confidence. A research audit found ~90% of the directive already built the day before (this section, above) — the two genuinely new, previously-uncovered pieces were built: `mark_implemented()` now captures a real `baseline_snapshot` (revenue via `channels/ledger.py::revenue_trend()`, reliability via `health_trend.py`'s real `GET /health` history, customer value via `customer_pipeline.py::funnel_conversion_summary()`); `measure_outcome(proposal_id, min_days_elapsed=7)` compares a fresh snapshot against that baseline no sooner than 7 real elapsed days later, honestly reporting IMPROVED/DEGRADED/NO_CHANGE/NOT_ENOUGH_DATA — scalability/automation/execution speed report an explicit `NO_REAL_SIGNAL`, never a fabricated number, since no real per-proposal signal for any of them exists in this factory. Each real call appends to the record's own `outcome_measurements` list — the actual trend, not a one-shot check. `run_daily_outcome_measurement_cycle()` (wired into `factory_loop.js`'s `maybeMeasureEvolutionOutcomes()`, same once-per-calendar-day gate) is the only automatic path; it never approves/rejects/marks-implemented. `rank_proposal()` is a disclosed heuristic over fields the record already has (`simulation.rollback_complexity`, `decision_flags`, keyword match on proposal text) — `strategic_value` is honestly `not_computed`, since `strategic_intelligence_core.strategic_score()` is per-niche and most evolution proposals are company-wide; never a fabricated numeric priority score. New department/product/AI-model proposal categories the directive also named were deliberately not built — no real underlying signal exists for any of them yet, same disclosed-gap discipline as `capital_allocation_engine.py`'s own "Reduce vs. Pause" gap. A real bug was found and fixed during this round: `_record_history()`'s own detail-logging on each measurement was silently resetting the elapsed-time clock used to gate the next measurement — fixed by storing `implemented_at` once, explicitly, rather than re-deriving it from a mutating `stage_history` list; covered by a named regression test. Mission Control gained `evolution-measured-outcomes` (`SERVICE_REGISTRY`, read-only) alongside the existing `evolution-queue` panel (which now also carries each entry's `ranking`).

New Observe signals live in `customer_pipeline.py`: `funnel_conversion_summary()`, `delivery_delay_summary()`, and a stuck-`PROPOSED` ("abandoned at proposal") check alongside the existing stuck-`NEW` one — all honestly empty/Unknown today (zero real customer traffic). `knowledge_graph/build.py` gained a `Proposal` node type (mechanical parse of `data/evolution_queue_state.json`, same non-semantic discipline as its `Lesson`/`ADR` nodes) — the real Learning History. Mission Control's `evolution-queue` panel is read-only passthrough over `evolution_queue.py::list_evolution_queue()`; `founder_console.py` surfaces the real `AWAITING_FOUNDER_APPROVAL` count alongside its existing DEFERRED-decisions count.

### Global Commercial Hardening — Marketplace Publish Protection Layer

`channels/publish_protection.py` (new, ADR-134, 2026-07-29): a real, disk-persisted (atomic write, `data/publish_protection_state.json`) pre-publish gate — per-arm daily/hourly caps, a real time-based cooldown after repeated failures, minimum publish spacing, a disclosed `risk_score` heuristic, and a global emergency stop. `PLATFORM_PROFILES` names Amazon KDP, Etsy, Gumroad, Payhip, Shopify, and AliExpress even though only Gumroad/Etsy/Payhip/Paddle have a real registered `channels/base_arm.py` arm today (KDP/Shopify/AliExpress are genuinely greenfield) — a conservative `_default` profile covers any arm name generically.
