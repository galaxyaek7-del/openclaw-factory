### Strategic Intelligence Core

`strategic_intelligence_core.py` (new, ADR-137, 2026-07-29) is the founder's named "Executive Brain" directive — a top-level decision layer answering 10 strategic questions, a named 11-dimension "Strategic Score," a once-per-cycle "Executive Brief," and multi-year thinking. A research audit found most of this already built the previous day under different names (`ceo_decision_center.py::answer_ceo_questions()`/`ceo_dashboard()`, `value_engine.py`'s 17-dimension `dimensions` dict, `scheduler.py::decide_next_actions()`'s accelerate/pause buckets, `evolution_engine.py`'s bottlenecks) — this module's real job is three genuinely new, narrow pieces, each a citation layer, never a second judgment engine.

`evaluate_strategic_horizons()` — 30d/90d/1y/3y/10y, each honestly `"NOT ENOUGH EVIDENCE"` today: the short horizons because `growth_engine.growth_forecast()` itself has no real windowed-comparison algorithm yet even at `REAL` maturity, the long horizons because this factory (founded 2026-07-05) cannot possibly have 2 real comparable multi-year sales windows yet — never a projected guess. `strategic_score(niche)` — the 11 named dimensions as `{value, source, reason}`, via `_extract_signal()`, a real normalizer over the genuinely different real shapes this factory's signals already arrive in (`{"value":...}`, `{"level":...}`, `{"favorability_score":...}`, `{"score":...}`, bare numbers, or `{"answer":"Unknown",...}`); Competition/Demand (`pain_level`)/Difficulty are sourced directly from `opportunity_pipeline.annotate_decision()` since `value_engine`'s own `dimensions` dict doesn't re-expose them. `build_executive_brief()` — the one real aggregator this factory never had, its 9 named fields each citing `resilience_monitor.assess_resilience()`, `ceo_decision_center.ceo_dashboard()`, `evolution_engine.build_evolution_report()`, `scheduler.decide_next_actions()`, `founder_console.build_founder_queue_partial()`, and this module's own horizon/customer-cost-trend signals for `research_needed` (honestly empty when every signal resolves).

`customer_pipeline.py::customer_problem_cost_trend()` (new Observe signal, same "recent-7d vs. trailing-daily-average" technique as `channels/ledger.py::revenue_trend()`) feeds `research_needed` alongside the horizons. Mission Control's `executive-brief` section returns `{report, markdown}` (same shape as `evolution_report`/`ai_doctor`/`department_health` — one dispatch serves both the live panel and `factory_loop.js`'s `maybeGenerateDailyExecutiveBrief()`, same once-per-calendar-day gate as those three). Every function here is read-only/recommend-only; Constitution-first and no-autonomous-high-risk-decisions were already real everywhere an irreversible action exists in this factory before this round began.

### Galaxy Council

`galaxy_council.py` (new, ADR-138, 2026-07-29) is the founder's "GALAXY COUNCIL — THE UNIFIED EXECUTIVE BOARD" directive: 10 named members, each producing `{opinion, confidence, evidence, risk, recommendation, founder_approval_required}`, honest disagreement never fabricated into a fake consensus. A research audit found `executive_board.py` (2026-07-22) already solves this exact class of problem once, under different member names (10 C-suite roles with real tally/consensus/disagreement/track-record-review) — the Council's real job is 9 new per-domain citation functions (Strategic/Market/Production/Customer/Financial/Security/Resilience/Innovation/Executive-Memory; Mission Control is the display venue, deliberately given no fabricated 10th opinion) plus a genuinely new N-way disagreement algorithm and a 3-way learning join, reusing `executive_board.py`'s tally/consensus pattern as the literal template rather than re-solving it. Three distinct rosters now exist (Constitution's 12 Councils, Executive Board's 10 C-suite roles, Galaxy Council's 10 named members) — deliberately not merged; see ADR-138 and the cross-reference note in `OpenClaw_Brain/06_Councils/README.md`.

Each member tags a `stance` (`proceed`/`hold`/`stop`/`no_data`/`informational_context`) only where its own real source already emits something genuinely comparable to a go/no-go signal (Financial's `accepted`, Production's `passed`, Market's critical/high alerts, Strategic's `at_risk` flag) — members whose sources are informational-only by their own docstrings (Security/Resilience/Innovation/Customer, all structurally company-wide-only — no niche field exists anywhere in their real data models) are never coerced onto that axis. `convene_council(niche)` calls all 9 every time (company-wide members tagged `scope: "company_wide"`, never silently skipped); `disagreement_detected` is true iff 2+ real-stance members genuinely disagree, generalizing `decision_engine.engine`'s real 2-signal-must-agree rule to N members — when they agree, `council_recommendation`/`council_confidence` cite that real agreement; when they disagree, both are honestly `"SPLIT — see disagreeing_members"`, never blended.

`data/council_recommendations.jsonl` (new, append-only) + `record_council_recommendation()` (explicit, human-triggered only) + `council_learning_summary()` close the Learning loop: a real 3-way join (Council Recommendation → the real Founder Decision that followed, via `decision_engine.store` → the real eventual Outcome) with the same `matched`/`diverged`/`pending`/`too_soon_to_tell` non-forced-verdict discipline as `executive_board.review_board_track_record()` — honestly `NOT ENOUGH EVIDENCE` until real triples accumulate, never backfilled. Mission Control: `convene-galaxy-council`/`record-council-recommendation` in `server.js`'s `ACTION_REGISTRY` (the correct precedent — `convene-executive-board`'s async-job/15-minute-timeout shape, not the company-wide `SERVICE_REGISTRY` 30-second-default shape, since a per-niche convening chains several real sub-calls), a niche-input button in `mission_control.html`'s Opportunities tab, and a no-input `galaxy-council-learning` panel in both `SERVICE_REGISTRY` and `mission_control_executive_v1.html`.

### Capital Allocation Engine

`capital_allocation_engine.py` (new, ADR-139, 2026-07-29) is the founder's "CAPITAL ALLOCATION ENGINE" directive: a continuously-updated 14-dimension "Investment Score" per initiative, dynamic resource recommendations, real opportunity-cost detection, and sunk-cost/shiny-object/founder-bias protection. A research audit found 7 of the 14 named dimensions directly duplicate `strategic_intelligence_core.py::strategic_score()`'s own 11 dimensions, built the immediately preceding round — `investment_score(niche)` delegates verbatim to `strategic_score()` for those 7 (never a second, competing citation function) and adds real citations only for the genuinely new 7 (Expected Revenue, Customer Impact, Market Defensibility, Engineering Cost, Maintenance Cost, Knowledge Reuse, Brand Value), sourced from `value_engine.compute_value_profile()`'s own dimensions/board_summary fields. 4 of those 7 turned out to already be honestly `Unknown` inside `value_engine.py` itself (`_NO_REAL_SOURCE_DIMENSIONS` + `estimated_maintenance_cost`) — no new code needed, only honest citation.

`opportunity_cost()` — the real, genuinely new gap: for every real ACCEPTED opportunity in `scheduler.py`'s own `wait`/`stop`/`cancel` buckets, cites which `run_now`/`accelerate` opportunities rank higher by the exact same real Priority Score order `value_engine.build_value_engine_report()` already computed — "resources are effectively going to X instead of Y," never invented. `stuck_without_production()` — "Projects Consuming Resources Without Results": a real ACCEPTED decision with zero real production attempt (`value_engine.classify_lifecycle_stage()`'s own real `prototype` stage) across a real, disclosed elapsed-time threshold, modeled on `customer_pipeline.py`'s existing stuck-request pattern. `build_capital_allocation_dashboard()` — the one real aggregator (Top ROI Initiatives, Projects Losing Value, Projects Consuming Resources Without Results, Resource Distribution, Expected Portfolio Return, opportunity-cost pairings), computing the real portfolio/scheduling scan exactly once and threading it through every field that needs it (measured live ~22-25s, given a disclosed 90s Mission Control timeout, same outlier class as `executive-brief`).

Sunk-cost-fallacy protection is documentation, not code: neither `profit_oracle.opportunity_score()` nor `value_engine.compute_value_profile()` accepts any cumulative-past-spend parameter anywhere in their real signatures — a decision here is architecturally incapable of being anchored to money already spent. The directive's "Reduce" vs. "Pause" and "Accelerate immediately" vs. "Increase" distinctions have no real signal anywhere today — disclosed as an honest gap in ADR-139, never fabricated. Mission Control: `investment-score` (per-niche, `ACTION_REGISTRY`, 15-minute timeout, same precedent as `convene-galaxy-council`) + a button in `mission_control.html`'s Opportunities tab; `capital-allocation-dashboard` (no-input, `SERVICE_REGISTRY` + `mission_control_executive_v1.html` panel).

### Executive Brain

`build_executive_directive()` calls those 4 systems + `channels/ledger.py::revenue_trend()` exactly once each — never a second competing computation — and adds only two genuinely new pieces: (1) `_candidate_directives()`/`_arbitrate()`, which tags every real candidate action already surfaced by those systems with the founder's own named Priority tier (1 System Stability → 5 Self Evolution) and picks the single lowest-tier one as the cycle's directive, honestly reporting a genuine same-tier tie as `SPLIT` rather than resolving it arbitrarily (same discipline as `galaxy_council.py`'s own disagreement handling); (2) a permanent append-only ledger (`data/executive_directives.jsonl`, same convention as `galaxy_council.py`'s `data/council_recommendations.jsonl`), mechanically parsed into a new `ExecutiveDirective` Knowledge Graph node type (`knowledge_graph/build.py`'s `_executive_directive_nodes()`, edges to a real `Proposal` node only when resolvable, never guessed). `requires_founder_approval` is always `True` — this module never calls `evolution_queue.approve_proposal()`, never reallocates capital, never publishes, never retires a business; every one of the 4 ADR-142 protected gates is untouched.

A real design bug was found and fixed during implementation: the first draft's Mission Control read handler defaulted to recording every view into the "permanent" ledger, which would have silently duplicated it on every page refresh — directly violating the directive's own "no duplicated knowledge" requirement. Fixed by splitting into `_executive_brain_directive()` (the live Mission Control view, `record_ledger=False`, verified live to never touch disk) and `_generate_daily_executive_directive()` (the one real path that grows the ledger, called only by `factory_loop.js`'s new daily tick step, same once-per-calendar-day gate as every other daily report). Verified live against real factory data: the expensive endpoint (chains 3 full-portfolio scans, measured ~59s, 120s Mission Control timeout) correctly arbitrated 43 real candidates down to a real Tier-1 finding (an unpinned npm dependency warning from `resilience_monitor`), not a fabricated one. Phase P2's "detect weak modules, propose, validate, run regression, reject unsafe, promote safe" was found to be, functionally, a re-description of the already-real `evolution_queue.py` pipeline (ADR-133/143) plus this session's own Architecture Review process — not rebuilt; the one genuinely missing piece (auto-running regression tests against a *proposed* change before founder review) is disclosed as an honest gap, not silently assumed to exist. Mission Control: `executive-brain` + `executive-directives-history` (`SERVICE_REGISTRY`), placed first in `mission_control_executive_v1.html`'s panel list per the founder's "single source of truth" ask, with the 4 most directly-reused existing panels cross-referenced in place rather than deleted (backward-compatible, per the founder's own "consolidate" answer).

### GF-OS — Enterprise Operating System

ADR-147 (2026-07-30) answers the founder's "Galaxy Forge Enterprise Operating System (GF-OS)" directive — the strongest overlap-and-conflict case this session has found. ### Affiliate Commerce

`affiliate_commerce/` (new, ADR-149, 2026-07-30) is the founder's explicit override of the ADR-148 Golden Rule deferral for one specific, narrow initiative — "this is NOT a temporary feature; it is a core business division alongside the digital-products arm." Unlike every other CEO-directive round this session, this one was not scoped down after research (no pre-existing overlapping module was found) — it was built exactly to the directive's own explicitly narrowed scope: one real affiliate network (Amazon Associates), one real product category (standing desk converters), real click tracking only.

`affiliate_commerce/products.py` holds a static, disclosed-source dataset of 4 real standing desk converters (real ASIN/price/rating/rating_count), sourced via a one-time manual browse of public Amazon search results on 2026-07-30 (not a live scrape, not a programmatic API call — disclosed in `SOURCE`) — ranked by a real, disclosed weighted-rating formula (`rating * log10(rating_count+1)`), never by Amazon's own paid ad placement. `affiliate_commerce/networks.py` builds real Amazon product URLs, honestly omitting the Associates tag (rather than fabricating a placeholder) until `AMAZON_ASSOCIATE_TAG` is actually set — which requires the founder's own real Amazon Associates account; this system cannot create that account (matches Claude's own standing "never create accounts" rule). `affiliate_commerce/click_tracking.py` is a real, append-only click ledger (`data/affiliate_clicks.jsonl`, same one-JSON-object-per-line discipline as `channels/ledger.py`) — clicks only, never conversions: a real conversion needs the affiliate network's real postback API, which does not exist for this factory yet.

The real customer-facing page (`customer_site/affiliate-standing-desks.html`, served automatically at `/site/affiliate-standing-desks.html` via the existing `express.static` mount) carries a real FTC-required Amazon Associates disclosure banner and a visible methodology citation — no fabricated reviews, no manipulative copy. Two new **public, unauthenticated** routes in `server.js` (`/api/affiliate/products`, `/api/affiliate/click/:product_id` — a customer_site visitor has no Mission Control login, same reasoning as the pre-existing `/api/customer/catalog`) back the page: the click route records a real click then issues a real `302` redirect to Amazon, honestly `404`-ing (not the generic 500) for an unknown product id. A separate, Mission-Control-authenticated `affiliate-commerce-status` `SERVICE_REGISTRY` entry (`mission_control_executive_v1.html`'s revenue group) gives the founder real click counts per product, real tag-configuration status, and an explicit not-implemented-yet list.

**What is honestly NOT implemented yet**: a real, approved Amazon Associates account (the founder's own real signup — this system never attempted it); real conversion/commission tracking (needs Amazon's real postback API); a second affiliate network; the SEO engine, multi-partner comparison, and auto-discovery the directive itself named as explicitly premature "before one real partnership is proven end-to-end."

**Permanent division status (ADR-150, 2026-07-30):** a same-day founder follow-up formally declared Affiliate Commerce a **permanent core business division alongside Digital Products** — not a one-off experiment — and asked for the complete long-term roadmap to be documented up front. GCID's roadmap is now written down (restated from ADR-148) but **zero GCID code is authorized** — ADR-148's original blocker (zero real dollars, `config/reality.json`'s `published_books: []`) is unchanged, and Phase 4 requires both that gate and Phase 3 to be substantially proven first.

**Global Affiliate Commerce Engine — full architecture, zero code (ADR-152, 2026-07-30):** a same-day follow-up directive asked for a 20-network unified connector architecture (`SearchProducts`/`GenerateAffiliateLink`/`TrackClicks`/`ImportCommissionReports`/`ValidateProgramStatus`/`UpdateCatalog`), a Mission Control Affiliate Commerce dashboard, a per-product Affiliate Intelligence layer, and tens-of-millions-of-products scale — flagged via `AskUserQuestion` before any code, since it directly contradicted the founder's own words from the immediately preceding directive ("No further expansion of Affiliate Commerce should occur until a real affiliate account is approved and connected") and skipped past ADR-150's own Phase 2/3 gates, none of which are met (`AMAZON_ASSOCIATE_TAG` still unset). **Founder's answer: document the complete architecture, build zero code** — same resolution as ADR-148 (GCID). ADR-152 is the detailed design for ADR-150's Phase 3/4 (registry pattern modeled on `ai_capability/registry.py`'s real `DISCOVERY`/`LIVE` status convention, an `AffiliateConnector` abstract interface, per-field honest-vs-`Unknown` sourcing for the intelligence layer, a disclosed database-scale gap) — a reference for when Phase 3's real gate clears, not a build authorization. ### Simulation-First Company Build

ADR-153 (2026-07-30, same day as ADR-149/150/152) answers the founder's "Simulation-First Company Build" directive — every commercial division should reach production quality via **Build → Simulate → Validate → Integrate → Launch**, with a config-only Simulation↔Production switch and a per-division Launch Readiness Score. This directly resolves the tension ADR-152 flagged and left open (a connector can't be honestly "production-ready" without real credentials, so ADR-152 said a connector is "either fully real... or does not exist as code at all") — **Simulation Mode** is the missing middle category: real product data/prices/catalogs, but explicitly and permanently labeled *simulated* purchases/commissions/payouts, never presented as real revenue. Research found this isn't a new pattern — it generalizes an already-real one: every distribution arm's `PublishResult.dry_run: bool` (`channels/base_arm.py`) plus `distributor.py`'s `dry_run=True`-by-default plus `reality.py`'s own real filter (`if event.get("dry_run") is not False: continue`, line 141) already keep dry-run activity out of real ground truth. "Simulation Mode" is that exact discipline, generalized from "don't really publish" to "don't really transact," given a company-wide name.

**Scope, surfaced explicitly before building (`EnterPlanMode`)**: the directive names 5 divisions (Affiliate Commerce, Digital Products, SaaS, AI Services, Licensing) and asks to expand "all business divisions in parallel" — but SaaS/AI Services/Licensing have zero real code or product concept anywhere in this factory (not part of `CLAUDE.md`'s own six-track vision). `simulation_mode.py` (new, repo root — `lib/` is JS-only in this codebase): `is_simulation_mode(division)` (per-division env var, e.g. `AFFILIATE_MODE`, defaults to `"simulation"`) + `tag_simulated()`. One flag per division (never global), matching `safe_mode.py`'s real per-subsystem-independence principle (ADR-135). `affiliate_commerce/simulation.py` (new): `run_simulation_cycle()` walks the **real** click ledger and simulates conversions at a disclosed, labeled `ASSUMED_CONVERSION_RATE` (2%, an industry baseline — this factory has zero real conversions to measure its own rate from) and `ASSUMED_COMMISSION_RATE` (3%, Amazon's published baseline rate, unconfirmed since no real account exists); every event writes to its own separate ledger, `data/affiliate_simulation_events.jsonl`, never the real `data/affiliate_clicks.jsonl`/`finance_data.json`/`config/reality.json`. `simulate_conversion()` is guarded by `is_simulation_mode()` — verified live to raise `RuntimeError` under `AFFILIATE_MODE=production`, not just documented as unsafe. The Amazon connector's real validation checklist before flipping to production is **exactly ADR-150's own Phase 2 gate** (real tag configured, real confirmed conversion, sustained real click data) — this directive doesn't loosen it, only gives the founder a way to exercise the pipeline before it clears. Rollback is a pure config revert (`AFFILIATE_MODE` back to `"simulation"`) — production code paths (`networks.py`/`click_tracking.py`/`products.py`) were never touched.

`launch_readiness.py` (new): a per-division 8-dimension scorecard (Architecture/Automation/Testing/Compliance/Monitoring/Documentation/Integration/Operational readiness) — distinct from `executive_score.py`'s company-wide score — every dimension a real, mechanical, disclosed-heuristic check (file existence, real `def test_` counts, real text-marker presence in `server.js`/`CLAUDE.md`/`mission_control_executive_v1.html`), never a semantic judgment. SaaS/AI Services/Licensing report every dimension as real, honest `not_architected`. Mission Control: `affiliate-simulation-report` (deliberately uncached — each read triggers a fresh real simulation cycle) and `launch-readiness-score`, both new `SERVICE_REGISTRY` entries + panels — the simulation panel carries a `⚠` prefix and is placed directly beside (never merged with) the real `affiliate-commerce-status` panel.
