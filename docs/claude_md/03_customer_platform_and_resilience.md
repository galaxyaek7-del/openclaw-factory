### Customer Platform

`customer_site/` is Galaxy Forge's real public customer-facing platform, served at `/site/` — a separate, English, dark-themed surface from the founder-facing Arabic Mission Control. Built across Phase 1/2 Round 1 (ADR-129/130, 2026-07-25) and Rounds 1-6 (ADR-131, 2026-07-29). Real end-to-end pipeline: intake → Qualification/Pricing (reuses `decision_engine.evaluate_and_decide`/`profit_oracle.butter_price`, the same real engines every internal opportunity uses) → real contract generation + typed-name e-signature acceptance → real Paddle checkout attempt → real payment-completion check + invoice → honest Production/QA/Delivery routing → real download center → real customer reviews.

- **Accounts**: `lib/customer_auth.js` (scrypt password hashing, its own signed-cookie session — deliberately separate from Mission Control's `mc_session`, zero new npm dependencies). `POST /api/customer/signup|login|logout`, `GET /api/customer/session`, `customer_site/login.html`. Guest (no-login) submission remains fully supported; a logged-in visitor's `account_id` is stamped onto their request for later history matching (by `account_id` OR email, reconciling pre-account guest requests).
- **The pipeline** (`customer_pipeline.py`, all commands spawned directly from `server.js`, not via `mission_control_api.py` — a different, customer-facing trust boundary): `advance_request` → `approve_request` (now requires `accepted_name`, a real contract e-signature via `contract_generator.py`) → `_attempt_payment_verification` → `check_payment_status`/`check_all_awaiting_payments` (real Paddle transaction confirmation + `invoice_generator.py`) → `_fulfill_paid_request` (honest routing: reuses an already-published `books/_generation_log.jsonl` artifact for a matched catalog product, else the side-state `PENDING_FOUNDER_FULFILLMENT` for a genuinely bespoke request, resolved via the founder's own `fulfill_manually()`) → `list_requests_for_account`/`submit_review`/`mark_followed_up`.
- **Real gap disclosed, not built**: customer-facing email/SMS notification is 0% built — the pull-based `customer_site/status.html`/`history.html` pages are the real substitute today. Every stage transition still notifies the founder via the existing Telegram channel.
- **Still genuinely blocked**: Paddle's account-onboarding gate (`transaction_checkout_not_enabled`) — every `PAID`-and-later code path is real but stays functionally unexercised against a live account until the founder clears it in `vendors.paddle.com` (`scripts/check_paddle_checkout_status.py` re-checks this live, never from cache).
- **Mission Control** gained a real executive cockpit for all of the above: `mission_control_executive_v1.html`'s card grid has panels for Customer Accounts, the Customer Pipeline, the Production/Fulfillment Queue, Invoices, and Reviews — all pure passthrough over the real state above, zero new dashboard file, zero fabricated metrics.

### Autonomous Company Evolution Engine

`evolution_queue.py` (new, ADR-133, 2026-07-29) is the real Observe → Think → Simulate → Decide → Execute → Learn → Protect → Dashboard pipeline the founder's "AUTONOMOUS COMPANY EVOLUTION ENGINE" directive asked for. **Execute is, by explicit founder decision, human-gated always — this must not be loosened without asking again.** No proposal, regardless of its computed risk tier, executes automatically: every real proposal from `tool_intelligence/proposals.py::list_proposals()` (6 real signal sources as of Global Trust & Resilience Layer Round 1, 2026-07-29 — bottlenecks, technical debt, capability gaps, a stuck-customer-funnel signal, a marketplace-publish-protection signal, and a health-degradation-trend signal) is intook, mechanically simulated (`affected_modules`/`rollback_complexity`/`sensitive_areas_touched` — a disclosed static evidence-text heuristic, not a real execution sandbox), and decided (real `policy_risk`/`duplicate_architecture_risk` flags, never an auto-approve/auto-reject) into a real state machine in `data/evolution_queue_state.json`: `PROPOSED → SIMULATED → AWAITING_FOUNDER_APPROVAL → APPROVED/REJECTED → IMPLEMENTED`.

`factory_loop.js`'s daily tick (`maybeGenerateDailyEvolutionQueueIntake()`) runs intake/simulate/decide once per calendar day — it stops at `AWAITING_FOUNDER_APPROVAL` and never calls approve/reject/mark-implemented. Those three are exclusively founder-triggered Mission Control actions (`POST /api/v1/actions/approve-evolution-proposal|reject-evolution-proposal|mark-evolution-proposal-implemented`, each requiring `{ proposal_id }`) — the one concrete code enforcement of "human-gated always," not just a policy note. `mark_implemented()` only closes the loop after a real, separately-reviewed Claude Code session has actually shipped an `APPROVED` proposal; there is no code path that writes production code from this system itself. Its `note` field is this factory's real "lessons learned" record (Decision Memory, Round 6, 2026-07-29) — not duplicated with a second field elsewhere.

**Outcome measurement + ranking (ADR-143, 2026-07-30)**: the founder's follow-up "AUTONOMOUS EVOLUTION ENGINE" directive asked this pipeline to "continuously measure whether every implemented evolution actually improved" revenue/reliability/scalability/automation/customer value/execution speed, and to rank proposals by strategic value/revenue impact/execution cost/long-term sustainability/risk/confidence. A research audit found ~90% of the directive already built the day before (this section, above) — the two genuinely new, previously-uncovered pieces were built: `mark_implemented()` now captures a real `baseline_snapshot` (revenue via `channels/ledger.py::revenue_trend()`, reliability via `health_trend.py`'s real `GET /health` history, customer value via `customer_pipeline.py::funnel_conversion_summary()`); `measure_outcome(proposal_id, min_days_elapsed=7)` compares a fresh snapshot against that baseline no sooner than 7 real elapsed days later, honestly reporting IMPROVED/DEGRADED/NO_CHANGE/NOT_ENOUGH_DATA — scalability/automation/execution speed report an explicit `NO_REAL_SIGNAL`, never a fabricated number, since no real per-proposal signal for any of them exists in this factory. Each real call appends to the record's own `outcome_measurements` list — the actual trend, not a one-shot check. `run_daily_outcome_measurement_cycle()` (wired into `factory_loop.js`'s `maybeMeasureEvolutionOutcomes()`, same once-per-calendar-day gate) is the only automatic path; it never approves/rejects/marks-implemented. `rank_proposal()` is a disclosed heuristic over fields the record already has (`simulation.rollback_complexity`, `decision_flags`, keyword match on proposal text) — `strategic_value` is honestly `not_computed`, since `strategic_intelligence_core.strategic_score()` is per-niche and most evolution proposals are company-wide; never a fabricated numeric priority score. New department/product/AI-model proposal categories the directive also named were deliberately not built — no real underlying signal exists for any of them yet, same disclosed-gap discipline as `capital_allocation_engine.py`'s own "Reduce vs. Pause" gap. A real bug was found and fixed during this round: `_record_history()`'s own detail-logging on each measurement was silently resetting the elapsed-time clock used to gate the next measurement — fixed by storing `implemented_at` once, explicitly, rather than re-deriving it from a mutating `stage_history` list; covered by a named regression test. Mission Control gained `evolution-measured-outcomes` (`SERVICE_REGISTRY`, read-only) alongside the existing `evolution-queue` panel (which now also carries each entry's `ranking`).

New Observe signals live in `customer_pipeline.py`: `funnel_conversion_summary()`, `delivery_delay_summary()`, and a stuck-`PROPOSED` ("abandoned at proposal") check alongside the existing stuck-`NEW` one — all honestly empty/Unknown today (zero real customer traffic). `knowledge_graph/build.py` gained a `Proposal` node type (mechanical parse of `data/evolution_queue_state.json`, same non-semantic discipline as its `Lesson`/`ADR` nodes) — the real Learning History. Mission Control's `evolution-queue` panel is read-only passthrough over `evolution_queue.py::list_evolution_queue()`; `founder_console.py` surfaces the real `AWAITING_FOUNDER_APPROVAL` count alongside its existing DEFERRED-decisions count.

### Global Commercial Hardening — Marketplace Publish Protection Layer

`channels/publish_protection.py` (new, ADR-134, 2026-07-29): a real, disk-persisted (atomic write, `data/publish_protection_state.json`) pre-publish gate — per-arm daily/hourly caps, a real time-based cooldown after repeated failures, minimum publish spacing, a disclosed `risk_score` heuristic, and a global emergency stop. `PLATFORM_PROFILES` names Amazon KDP, Etsy, Gumroad, Payhip, Shopify, and AliExpress even though only Gumroad/Etsy/Payhip/Paddle have a real registered `channels/base_arm.py` arm today (KDP/Shopify/AliExpress are genuinely greenfield) — a conservative `_default` profile covers any arm name generically.

**CORRECTION (2026-10-12): "KDP ... genuinely greenfield" is stale.** `channels/kdp_arm.py` (335 lines, `KdpArm`, same `BaseArm` contract as every other arm) was committed later the same session cycle (`8f5372a`) and self-registers as the real `'kdp'` arm — confirmed live this round: `import distributor; [a.name for a in channels.registry.all_arms()]` → `['gumroad', 'payhip', 'etsy', 'paddle', 'x', 'kdp']`. KDP has no public publishing API (Amazon doesn't offer one) so this is an honest, credential-gated **manual-upload** adapter — `dry_run=False` is permanently blocked in code, real publication always requires a human to actually upload at kdp.amazon.com — but the integration itself (metadata mapping, duplicate detection, error classification, the full `PlatformAdapter` extended contract) is real and committed, not greenfield. It reports `ArmStatus.UNAVAILABLE` only because `KDP_USERNAME`/`KDP_SESSION_COOKIE` aren't set in `.env` — the same class of founder-only credential gap as every other channel, not a missing integration. Zero test coverage existed for this module anywhere in the tracked suite until this same round added `tests/test_universal_fabric_stage01.py` (18 tests, real, passing via the actual CI entrypoint).

`distributor.py::distribute()` calls `check_publish_allowed()` immediately before every real (non-dry-run) `arm.publish()` — a blocked arm never reaches the real platform call. Dry runs are exempt entirely (no real-world effect to protect against). `channels/ledger.py::record_publish_attempt()` gained optional `risk_score`/`protection_decision` kwargs, omitted from the event when not given — every pre-existing caller's event shape is unchanged. Mission Control exposes a read-only `publish-protection-status` panel plus founder-only `publish-emergency-stop`/`publish-emergency-resume` sync actions (`POST /api/v1/actions/...`, mirroring `pause-production`/`resume-production`'s exact shape) — never fired automatically. `founder_console.py` surfaces an active emergency stop as a real pending-decision item; `executive_score.py` gained a `publishing_safety` sub-score; `tool_intelligence/proposals.py` gained a dynamic generator, `_marketplace_protection_proposal()` (see Autonomous Company Evolution Engine above).

`executive_quality_gate.py::check_content_neutrality_risk()` (Executive Safety Principles, same directive) is a new named hard-reject criterion — a real phrase-list content scan for the founder's explicit "never evolve toward: political activity, religious discussions, ethnic classification, sensitive personal profiling, illegal content, hate content, manipulation, privacy violations, government interference" list, permanently recorded in `OpenClaw_Brain/00_Governance/EXECUTIVE_SAFETY_PRINCIPLES.md`.

**Explicitly deferred, not built**: a Global Partner/Affiliate/Commission Engine and broader Commercial Maturity (subscriptions, B2B/enterprise licensing) — real research this session found zero scaffolding exists and, more fundamentally, no payables/liability ledger exists anywhere in this factory's financial model (`finance_data.json`/`channels/ledger.py` record revenue only). Building a commission engine without that primitive first would risk fabricated financial bookkeeping. See ADR-134 for the full design sketch reserved for that future round.

### Global Trust & Resilience Layer

Global Trust & Resilience Layer (ADR-135, 2026-07-29) closed a handful of real, scoped gaps found by research against this directive's 10 priorities — most of it was already built by the two directives above.

- **Self-Diagnosis**: `lib/health_trend.js` (real recording — `factory_loop.js`'s tick already fetches a real `GET /health` status every cycle; this appends it to `data/health_snapshots.jsonl`) + `health_trend.py` (the Python-side mirror, same per-language-reimplementation precedent as `executive_score.py`'s `_dual_inspection_pass_rate()`). `detect_health_degradation()` is a real, disclosed mechanical trend heuristic over real recorded history — never a fabricated prediction.
- **Safe Mode**: `safe_mode.py` (new) generalizes the existing per-arm circuit breaker to three real named subsystems — `ai_generation`/`market_intelligence` (their own independent flag) and `marketplace_publishing` (deliberately no independent flag — reads `channels/publish_protection.py`'s own global emergency stop directly, never duplicated). Mission Control: `safe-mode-status` panel, `mark-subsystem-unstable`/`clear-subsystem-unstable` actions.
- **Global Policy Engine**: `executive_quality_gate.py` gained `check_constitution_alignment()` (a real, informational-only citation of which `CONSTITUTION.md` principles a decision's already-running checks actually satisfy — never a new hard gate) and `check_platform_tos_awareness()` (honestly `UNKNOWN` always today — zero platform Terms of Service text is parsed anywhere in this factory; a disclosed gap, never a fabricated PASS).
- **Founder Protection**: the founder's explicit resolution to a real conflict — proven arms (`gumroad`/`etsy`/`payhip`/`paddle`) keep their existing autonomous publishing unchanged; `channels/publish_protection.py` now also blocks a genuinely new arm's first-ever real publish, and any publish whose `risk_score` crosses a real high-risk threshold, until a real founder-only `approve-first-publish`/`approve-elevated-risk-publish` Mission Control action clears it (the latter single-use, consumed by the very next real attempt).
- **Human Trust**: `profit_oracle.py::opportunity_score()` gained a parallel `components_basis` dict tagging each component `"real"` (a live signal actually fed it) or `"estimated"` (a fixed per-tier constant or keyword heuristic) — read-only metadata, the real `components`/`accepted` values are unchanged.
- **Decision Memory**: `decision_engine/types.py::Decision` gained optional `alternatives_rejected`/`expected_outcome` fields. The real "actual outcome" pipeline (`decision_engine/feedback.py::sync_outcomes()` → `data/decision_outcomes.jsonl`) already existed and was already wired — the gap was that it was never linked into company memory; `knowledge_graph/build.py` now adds a real `Outcome` node with a `resulted_in` edge back to its `Decision` node, mechanically joined by `decision_id`, only for a real matched outcome.
- **Continuous Improvement**: `evolution_engine.py::build_evolution_report()` gained `customer_success_bottleneck`, reusing (not duplicating) `tool_intelligence.proposals`' own real customer-funnel signal, framed explicitly around customer success.
- **Reputation Protection**: confirmed no fabrication path exists anywhere in this factory (reviews/finance/analytics are real-input-only) — `channels/publish_protection.py`'s existing rate/cooldown state is documented as the real anti-spam/anti-aggressive-publishing control, not duplicated.
- **Resilience Tests**: `tests/test_resilience.py` (new) — a real, mocked fault-injection suite (never a live chaos system against real production data) proving cross-cutting recovery properties across `distributor.py`, `factory_state.py`, `channels/publish_protection.py`, `safe_mode.py`, and `recovery/startup_check.py` that no single module's own unit tests already covered.

### Continuous Trust & Resilience Monitoring

`resilience_monitor.py` (new, ADR-136, 2026-07-29) is the real Monitor + Classify + Learn aggregator the founder's follow-up directive asked for — "transform the [Global Trust & Resilience] layer into a permanent monitoring system," not more isolated fixes. Every signal it uses already existed (`safe_mode.py`, `channels/publish_protection.py`, `customer_pipeline.py`'s `needs_attention`, `ai_doctor.py`'s dependency-pinning, `health_trend.py`); this module's only genuinely new pieces are a shared 4-tier severity vocabulary (`informational`/`warning`/`critical`/`emergency` — no existing signal used this exact scale) and a real incident-memory record.

`assess_resilience()` classifies every monitored area and computes a transparent `resilience_score` — the exact `executive_score.py` precedent (an average of only the real, data-available findings, informational only, disclosing how many were excluded and why, never gating anything). `record_incident()`/`list_incidents()` (`data/incidents.jsonl`, new) open a real incident only on a genuine new critical/emergency finding (deduped — an already-open incident is never re-recorded on a later tick) and close it with a real "resolved" event once the condition clears; every Learn field (`root_cause`, `prevention_rule`, `detection_rule`, `improvement_proposal_id`, `rollback_guidance`) is either a real evidence-cited template or honestly `None`/`"Unknown"` — `improvement_proposal_id` specifically is only ever cited when that id is **actually present** in `tool_intelligence.proposals.list_proposals()`'s real, live output, never a static guess.

Mission Control: `resilience-status` (merges the Python signals with `computeHealthStatus()`'s `storage_integrity` and `lib/dashboard_data.js`'s reviews/support-tickets, same merge pattern as `executive-score`) and `resilience-incidents`, both read-only. `factory_loop.js`'s `runResilienceMonitorTick()` runs **every tick** (not daily-gated, the honest definition of "real-time" a scheduler-less factory can offer) but adds zero new auto-executing code path — it never calls `trigger_emergency_stop()`/`mark_subsystem_unstable()` itself; every irreversible/high-impact lever stays exactly as founder-gated as ADR-134/135 left it.
