# ADR-145 — Executive Decision Memory

**Date:** 2026-07-30
**Status:** Adopted.

---

## The directive

"MISSION: Executive Decision Memory (P0 Only)... Do NOT build any new business modules." Record every executive decision as structured knowledge with a unique Decision ID, timestamp, source modules, evidence, confidence, expected outcome, and final approval status; prevent duplicate decisions; detect conflicts with previous decisions; let Mission Control explain WHY any decision was made; track outcomes over time; continuously improve future decisions using historical evidence. Constraints: zero breaking changes, no architecture expansion, no duplicated logic, no fabricated metrics, no placeholder values, reuse the existing Knowledge Graph/Executive Brain/Mission Control, 100% backward compatible.

## What research found already real, before any code was written

`decision_engine/` (ADR-050/076) already owns almost this entire objective list for niche decisions: `Decision.decision_id` (a real deterministic hash, `make_decision_id()`), `decided_at`, `status` (the real final approval status: ACCEPTED/REJECTED/DEFERRED/RESEARCH_REQUIRED), `reasoning`, `evaluation_snapshot` (the real evidence, confidence nested inside it), and — Decision Memory, Round 6, 2026-07-29 — `alternatives_rejected`/`expected_outcome`. `decision_engine/feedback.py::sync_outcomes()` already tracks real outcomes over time (`data/decision_outcomes.jsonl`). `decision_engine/learning.py::recalibration_report()` already computes real per-dimension "did this signal actually predict a sale" statistics from historical evidence — Objective 8 at the honest, human-reviewed-before-applying level this factory's standing policy requires (its own docstring: "does not automatically modify the live scoring logic; needs a separate decision to apply it") — not rebuilt. `knowledge_graph/build.py` already has real `Decision`/`Outcome` nodes with a `resulted_in` edge, a real `ExecutiveDirective` node type (ADR-144, this same session), and a real, generic `query_related()` traversal primitive.

Two things were genuinely missing, confirmed by reading the code rather than assumed: `decision_engine/store.py::append_decision()` has zero duplicate-prevention logic — it appends unconditionally, always has. And no function anywhere in the codebase assembles a single "why was this decision made" narrative for an arbitrary decision_id. This ADR adds exactly those two things, plus the unified read-model Mission Control needs, over the two already-real ledgers — never a third, competing store.

## What was built

**Additive fields on `executive_brain.py`'s own ledger** (`data/executive_directives.jsonl`, ADR-144) — the directive's own "Reuse Executive Brain" instruction, taken literally: `_make_directive_id()` gives every Executive Directive a real deterministic ID, same sha256-truncate convention as `decision_engine.types.make_decision_id()` (not a call into that function — its signature is niche-specific; same technique, applied honestly to a domain object that isn't always about a niche). `_confidence_estimate()` is a disclosed heuristic (never a fabricated number) — `high` only for a single unambiguous real-evidence-backed winner, `low` for a genuine `SPLIT`, `n/a` for `NO_ACTION_NEEDED`. `_detect_repeat()` is the real "prevent duplicate decisions" mechanism: a mechanical check (never semantic) against the most recent ledger entries — an identical (action, tier) recommended again is honestly tagged `is_repeat_of` the prior decision_id rather than presented as N independent decisions, while still being recorded (the underlying alert may genuinely still be active; dropping it would lose real information).

**New module `executive_decision_memory.py`** — the two genuinely new functions:

- `detect_niche_conflict()` / `detect_ledger_conflicts()` — real, mechanical conflict detection (a disclosed keyword-based action-stance classifier, same discipline as `evolution_queue.py`'s `SENSITIVE_AREA_KEYWORDS`), never a semantic/AI judgment. The niche check cites `decision_engine.store.find_decisions_by_niche()` directly — a directive proposing action on a niche that already carries a real REJECTED decision is a real, checkable conflict. The ledger check finds the same real niche recommended both "accelerate" and "stop" within a lookback window across recent Executive Directives. Verified against real factory data: correctly found zero conflicts today (honest, not padded) and correctly flagged a fabricated same-niche opposing-stance pair in testing.
- `explain_decision(decision_id)` — the real "why" function, dual-lookup across both real ledgers (whichever one actually carries the id), reusing `knowledge_graph.build.query_related()` directly for connected real nodes (Outcome/Proposal/ADR) rather than writing a second traversal. Prefers the last saved real Knowledge Graph snapshot over a live rebuild — reuse before recompute, same discipline as `executive_brain.py`'s own `_knowledge_growth_trend()`. Verified live against a real niche decision from `data/decisions.jsonl`: returned the real reasoning, evidence, and conflict-check trail.
- `list_decision_memory()` — the Mission Control unified read-model: merges the two real ledgers (niche decisions + Executive Directives) into one chronologically-sorted view, each row tagged with its own real `decision_id`/`status`/`type`. Pure read + merge-sort, no new computation, no dashboard rebuild — cheap by design (confirmed instant over live HTTP).

## What stays exactly as it was

Zero new execute-capable code path. Nothing here approves, rejects, publishes, reallocates, or auto-applies a recalibration. `append_decision()`/`_append_ledger()` are unchanged — duplicate detection is a read-side annotation, not a write-side rejection, so no existing caller's behavior changes (a real repeat is still recorded, honestly labeled, never silently dropped — silently dropping a still-active alert would itself be a form of fabrication-by-omission).

## Mission Control

`mission_control_api.py` gained `decision_memory_list`, `decision_memory_conflicts`, `decision_memory_explain` (the last reads `{decision_id}` from its payload). `server.js`'s `SERVICE_REGISTRY` gained `decision-memory`, `decision-memory-conflicts` (both cheap, no-input), and `decision-memory-explain` (`?decision_id=` query param, same precedent as the existing `product-concept-comparison` panel's `?niche=` pattern — an honest empty-state message when no id is passed, never a guessed default). `mission_control_executive_v1.html` gained three new panels, placed immediately after the existing Executive Brain panels, distinct from (not duplicating) the pre-existing `decision-history` panel — that one lists niche decisions only; this one is the merged, decision-memory-specific view the directive asked for.

## Validation

`tests/test_executive_decision_memory.py` (new, 16 tests): action-stance keyword classification, niche-conflict detection against both a real REJECTED and a real ACCEPTED prior decision, ledger-conflict detection (same-niche-opposing-stance is flagged, same-niche-same-stance and different-niche pairs are honestly not), `explain_decision()` for both a real niche decision and a real Executive Directive plus an honest not-found case, and `list_decision_memory()`'s merge-sort ordering. `tests/test_executive_brain.py` gained 9 more tests (46 total, all passing) covering `_make_directive_id()` determinism and `_detect_repeat()`/`_confidence_estimate()`'s real behavior. Verified live over a real logged-in HTTP round-trip: `decision-memory` (real merged data), `decision-memory-conflicts` (honestly empty today), and `decision-memory-explain` (both a real decision_id and the honest no-parameter empty state). `data/executive_directives.jsonl` confirmed still absent from disk after this session's testing — every test path used a temp ledger or a real read-only lookup, never the real one.
